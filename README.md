# Vault Transit auto-unseal — local two-node PoC (Windows)

A minimal proof of concept for the pattern where **one Vault node unseals another**,
written for Windows + PowerShell. One node ("unseal") runs the Transit secrets engine
and holds an encryption key; the other node ("service") hands its root key to that
engine to be wrapped and unwrapped at startup instead of using Shamir unseal shares.

```
  Unseal node (8200)                         Service node (8100)
  +----------------------+                   +----------------------+
  | Shamir-sealed        |  encrypt root key | seal "transit"       |
  | transit/autounseal   | <---------------- | root key (wrapped)   |
  | autounseal token     | ----------------> | no unseal keys       |
  +----------------------+  decrypt on boot  +----------------------+
```

## Dependencies

**Only the Vault CLI is required.** Unlike the bash version, the PowerShell scripts
parse JSON natively (`ConvertFrom-Json`), so there is no `jq` dependency.

- **Windows PowerShell 5.1** (built into Windows 10/11) or **PowerShell 7+**. Both work.
- **Vault CLI** on PATH. Pick one install method:

  | Method | Command (run in an elevated terminal) |
  |--------|----------------------------------------|
  | winget | `winget install -e --id Hashicorp.Vault` |
  | Chocolatey | `choco install vault` |
  | Scoop | `scoop bucket add main; scoop install vault` |
  | Manual | Download the Windows amd64 zip from `https://developer.hashicorp.com/vault/install`, unzip `vault.exe`, and add its folder to your PATH |

  Verify with `vault -v` (current line is v1.21.x / v2.0.0). OpenBao works too — install
  the `bao` binary and replace `vault` with `bao` throughout.

No Docker, no cloud KMS. Both nodes run as background processes on localhost with TLS
disabled and file storage, so the focus stays on the seal mechanism.

## Run it

Open PowerShell in this folder. Because these are unsigned local scripts, either set a
per-process bypass or invoke them with the bypass flag:

```powershell
# Option A: relax policy for this session only, then run normally
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\setup.ps1

# Option B: one-shot, no policy change
powershell -ExecutionPolicy Bypass -File .\setup.ps1
```

Teardown:

```powershell
.\teardown.ps1          # stop both nodes
.\teardown.ps1 -Wipe    # stop and delete all state/credentials/logs
```

`setup.ps1` does, in order:

1. Starts the unseal node, then `operator init` + `operator unseal` (1-of-1 Shamir, for PoC simplicity).
2. Enables `transit`, creates the `autounseal` key.
3. Writes a least-privilege policy (encrypt/decrypt on that one key only) and mints an
   **orphan, periodic** token for the service node.
4. Renders `config\service-vault.hcl` from the template with that token injected.
5. Starts the service node, runs `operator init` — because its seal is `transit`, init
   produces **recovery keys** (not unseal keys) and the node auto-unseals immediately.
6. Verifies the service node reports `Seal Type: transit, Sealed: false`.

## What the layout looks like after setup

```
config\
  unseal-vault.hcl          # checked in
  service-vault.hcl.tmpl    # checked in (token placeholder)
  service-vault.hcl         # generated by setup.ps1 (contains the token)
data\unseal, data\service   # file storage for each node
credentials\                # init output: keys + root tokens (PLAINTEXT)
logs\                       # server stdout/stderr per node (.out.log / .err.log)
pids\                       # background process PIDs
```

## Things worth poking at

**Restart the service node and watch it unseal with no keys:**
```powershell
Stop-Process -Id (Get-Content pids\service.pid)
Start-Process vault -ArgumentList 'server','-config=config\service-vault.hcl' -WindowStyle Hidden
$env:VAULT_ADDR='http://127.0.0.1:8100'; vault status   # Sealed: false — nothing entered
```

**The "who unseals the unsealer" problem** — the dependency this whole pattern hinges on.
Stop both, then start only the service node:
```powershell
Stop-Process -Id (Get-Content pids\unseal.pid),(Get-Content pids\service.pid)
Start-Process vault -ArgumentList 'server','-config=config\service-vault.hcl' -WindowStyle Hidden
$env:VAULT_ADDR='http://127.0.0.1:8100'; vault status   # stays Sealed until the unseal node is back
```
The service node can't unwrap its root key while the transit endpoint is unreachable.
The unseal node uses Shamir and must be unsealed manually (or by its own auto-unsealer
further up the chain). In production that root-of-trust is usually an HSM or cloud KMS;
in an air-gapped environment it's an on-prem HSM (PKCS#11 seal) or a small, tightly
controlled Shamir-sealed Vault whose key holders perform the manual unseal after a reboot.

## Why orphan + periodic for the autounseal token

Per HashiCorp's transit seal docs: the token must be an **orphan** so it isn't revoked
when its parent (the root token here) expires, and **periodic** so it stays renewable
indefinitely — Vault renews it automatically while the service node is running. If the
service node stays down past the token's TTL, the token can expire and the seal breaks;
you'd then mint a new token and update the seal stanza.

## PoC-only shortcuts (do NOT carry these into anything real)

- **TLS disabled** on both listeners. Real deployments use mutual TLS between the service
  node and the transit endpoint (`tls_*` params in the seal stanza).
- **1-of-1 unseal/recovery shares.** Production uses a real quorum (e.g. 5 shares,
  threshold 3) distributed across separate key holders.
- **Root tokens and unseal keys written to `credentials\` in plaintext.** Never do this
  off a throwaway laptop. Revoke the root tokens once you've set up admin auth.
- **File storage, single node each.** Production uses integrated storage (Raft) with a
  multi-node cluster for HA; the seal mechanism is identical, only `storage` and the
  cluster listener change.
- **Same host.** Real topology separates the transit/root Vault from the service Vault
  onto different hosts/networks.

## Windows-specific notes

- **Execution policy.** The scripts are unsigned; use one of the bypass methods above.
  This only affects how you launch them, not what they do.
- **Background processes.** Nodes launch via `Start-Process -WindowStyle Hidden` and their
  PIDs are recorded in `pids\`. If you reboot or kill the terminal, the `vault.exe`
  processes may keep running — `.\teardown.ps1` cleans them up, or use Task Manager.
- **Firewall prompt.** The first launch may pop a Windows Defender Firewall dialog because
  Vault opens a listener. Allow it for localhost (Private networks) — both nodes bind only
  to 127.0.0.1.
- **Paths.** Configs use forward-slash relative paths (`./data/unseal`), which Vault
  accepts on Windows. Keep the folder out of OneDrive-synced locations to avoid file locks.

## Migrating the seal later (good to know)

Changing the `seal` stanza triggers a seal-rewrap. To move the service node from transit
auto-unseal back to Shamir, you add `disabled = "true"` to its `seal "transit"` block,
restart, and run `vault operator unseal -migrate` with the recovery keys. Migrating the
other direction (Shamir -> auto) is the same idea in reverse.
